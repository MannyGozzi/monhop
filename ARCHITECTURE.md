# MonHop architecture

MonHop is a symmetric native peer application. Either computer can own the physical keyboard and mouse, including two computers on the same OS. No webview or JavaScript participates in capture, encoding, networking, ownership or injection.

The diagram below is one direction of the integrated flow. Every sharing session runs it both ways at once over one connection: each computer captures its own keyboard and mouse and injects the other's, and a shared floor lets only one direction be active at a time (see Bidirectional sessions). The desktop exposes pairing, a standing authenticated setup link for layout sync, and sharing; the CLI exposes diagnostics.

```text
Physical input
└─ native capture and injection-loop filter
   └─ bounded event queue
      └─ authoritative pressed state + virtual pointer + configured edge graph
         ├─ local ownership: let normal OS input continue
         └─ remote ownership: reliable state messages / latest ordered motion
            └─ pinned interface + pinned identity + TLS 1.3 QUIC
               └─ strict decoder + session/sequence validation + receiver watchdog
                  └─ destination-native injection
```

## Ownership boundaries

`monhop-core` owns canonical device/display identifiers, physical HID keys, semantic modifiers, held state, monitor links, crossing geometry and pointer ownership. It has no OS, disk or network effects. Transitions return actions to be performed by the native session coordinator.

`monhop-protocol` owns the small versioned binary protocol and decoder bounds. Reliable key/button/scroll/control events use ordered streams. Motion is independently sequenced and may use datagrams. Reusable caller-owned encode buffers avoid an allocation per motion event. Epochs distinguish sessions and transitions so stale input cannot be revived.

`monhop-transport` owns network policy, authenticated device identities and the eventual QUIC connection. A lock binds an exact interface snapshot, on-link route and peer. Revocation is irreversible for that lock. Interface address/subnet validation is only one boundary: the socket adapter must also enforce interface pinning and inspect arrival metadata.

`monhop-platform-windows` and `monhop-platform-macos` own native enumeration, capture, injection, permissions and protected identity storage. No platform module enables sharing as a side effect of loading or enumeration.

`apps/monhop` composes read-only and bounded passive diagnostics, plus separately selected protected identity creation/readback. The initial interface is a Rust CLI with no browser runtime. A future Tauri UI remains possible if its entire runtime network behavior, licenses and native command surface can satisfy SECURITY.md.

The separate Mac `native_window` example owns a temporary AppKit window and opts into `MacInjector::for_current_process()`. That constructor fixes all posts and cleanup to the current PID through `CGEventPostToPid`, with no caller-supplied target or fallback to global posting. The fixture consumes marked events from its own application queue before shortcut dispatch. It tests native delivery without authorizing a peer or affecting another application's input queue.

## Monitor and pointer model

Physical display geometry and configured layout are different. Each display retains its native pixels, logical dimensions, OS origin and scale. Explicit directed links connect chosen edge spans. A crossing position is normalized along the source edge and mapped to a point just inside the destination edge. Negative coordinates, portrait displays and unrelated gaps are valid. Overlapping ambiguous links are rejected.

Raw mouse deltas and OS-accelerated motion are distinct observations. The Windows prototype must measure both before choosing the final virtual-pointer acceleration policy. Datagram motion must either be absolute in the session's virtual coordinate space or accumulate independently of packet loss; dropping a relative delta must not permanently lose pointer displacement. Scroll stays reliable until evidence supports another design.

The Mac injector keeps the last submitted absolute pointer point instead of querying asynchronous OS cursor position for each relative event. It snapshots active display rectangles at construction and clamps motion to the nearest point on a valid display, not an enclosing rectangle that would admit gaps. Recreate the injector after display changes; live display-change revocation is still required in M4. An absolute move must anchor the state before relative moves or button presses. Failed event construction leaves the previous point intact. Recovery releases buttons at that point before clearing it. This removes the cursor-read race and edge-overshoot accumulation, but Quartz posting still provides no delivery acknowledgement or proof of physical input feel.

## Bidirectional sessions

A sharing session is two directional halves on one QUIC connection. Header byte 7 of every frame carries its scope: 0 for the connection itself (Hello, SessionSetup, Disconnect, Error, and the setup link), 1 for the half in which the lower DeviceId controls the higher, 2 for the reverse. Each half keeps the single-direction machinery unchanged — its own epochs, reliable sequence (starting at 3), heartbeats, holds and watchdog — because the other half's frames never reach its gates; `SessionIo` stamps the scope on send and routes by it on receive, and an unknown scope fails the session. `session::run_session` is the only sharing runtime: the outbound half (`SourceController` over native capture) controls the peer and the inbound half (`InputReceiver` behind the destination actor) injects the peer's input. Protocol version 9 carries the control permissions in `SessionSetup` (bit 0: lower may control higher, bit 1: the reverse). A turned-off direction keeps its half connected for health, treats every seam as a wall outbound and answers `ActivationDeclined(Disabled)` inbound.

The floor (`monhop_core::SharedFloor`, one atomic packing state and generation) keeps at most one direction active: Free, then Requesting, Sending and Returning owned by the outbound half, or Receiving and Yielding owned by the inbound half. Only the owning half changes or frees it, and only at its own generation, so a hold or cleanup in the idle half never touches the active one. A first crossing needs Free -> Requesting; reanchoring between peer displays stays inside Sending or Receiving. When both computers request at once the lower DeviceId wins and declines the other's request as `Contended`; a request that meets Sending or Returning is declined `Busy`. A declined crossing consumes its epoch, stays local, and retries that seam only after `DECLINE_RETRY_AFTER` (50 ms) of continued pressure.

Local input wins. While the floor is Receiving, the capture callback itself (`PhysicalCapture::process` through `TakeBackGate`) treats a key or button transition, a nonzero scroll, or relative motion of `TAKE_BACK_MOTION` (6 units) within `TAKE_BACK_WINDOW` (100 ms) as a take-back: it moves the floor to Yielding, closes injection admission for that generation only, and wakes the coordinator. The injector counts every real key or button down before it checks admission and uncounts it after the up, so the callback always sees whether injected input was down at the close; if it was, local input is withheld (presses dropped, their repeats and releases quarantined, and never counted in later modifier masks) for at most `MAX_SUPPRESSION_TTL` (120 ms) until the injector's release completes. On Windows the low-level mouse hook, the only place that can suppress motion before delivery, measures that travel itself. The inbound half releases everything it injected without waiting for the network, sends `TakeBack`, and keeps sequencing the peer's frames without injecting until ReleaseAll frees the floor; the peer's outbound half calls `request_local` when it is Remote or when its current transition settles there. Crossing detection is off while Receiving or Yielding, every captured event carries the floor generation it was captured under, and crossings re-arm from a fresh pointer poll when the floor returns to Free after being Receiving, so injected motion is never read back as a local crossing.

One `NativeSessionClaim` per process splits into a `CapturePermit` and an `InjectionPermit`; the claim clears only after both drop. Startup runs both halves' scoped health first, then the claim, then capture (so its held-key snapshot never contains injected keys), then the destination; nothing crosses or injects until both halves hand off, and a key held at capture start keeps every seam a wall until capture can suppress. Teardown closes injection admission, restores local routing, releases injected keys and buttons, completes the capture's release quarantine, stops native workers and only then drops the permits; none of it waits on the network. Display change, permission loss, the emergency chord on either computer, revocation, queue overflow and disconnect end the whole session. A display change on this computer (native capture's own display-change stop, the destination watchdog's 30 ms check, or a display list that cannot be read) ends as `SessionFailure::LocalDisplaysChanged` and closes with a reason the other computer reads as `LinkClose::PeerDisplaysChanged`; a user's own stop still ends as `Revoked`.

## Trackpad gestures

Protocol version 11 carries gestures as closed semantic messages, never as keys: `Gesture` (kind 21: Magnify and Rotate with phases, SmartMagnify, ForceClick) and `SystemGesture` (kind 22: Overview, AppWindows, DesktopPrevious/Next, ShowDesktop, Launcher, NavigateBack/Forward, NotificationCenter, Search, SwitchAppPrevious/Next), named by result, not fingers. Each receiver owns its mapping. Windows holds Left Ctrl from a pinch's Began to its end, posts one wheel notch per 10 % of scale and drops wire scrolls while the pinch is open; a system gesture is one atomic `SendInput` chord (Win+Tab, Ctrl+Win+Left/Right, Win+D) or an XButton click. macOS turns a pinch into Cmd+= / Cmd+- steps and a system gesture into the user's own symbolic hotkey, dropping it when that hotkey is disabled. Nothing starts a process on a peer's behalf.

The macOS capture tap adds CG types 29, 30 and 31, whose fields are private; the Dock-swipe direction signs are one constant per axis in `capture_decode.rs`. `monhop_core::GestureLatch` fixes a touch session's route when it opens, so a gesture that began locally finishes locally and one that began while controlling the peer is withheld from the Mac until it ends. A Dock swipe fires its one system gesture mid-swipe, once its progress reaches `DOCK_SWIPE_COMMIT_PROGRESS`. The receiver repairs phase order, ends an open gesture after `TOUCH_STREAM_IDLE` (500 ms) without a record, sends `EndGestures` before every release, and counts the pinch Ctrl and each chord as injected presses for take-back. Windows touchpad capture is not built: a Windows touchpad's gestures stay on that PC.

## Failure and security behavior

No unpaired or unvalidated session reaches the injector. Local input remains active at startup. A transition is acknowledged only for the current epoch and expected destination. Disconnect, heartbeat timeout, queue overflow and emergency escape restore physical ownership and release all managed remote keys/buttons. Release and hook teardown must be independent of a live network.

Pairing is an explicit trust change. Device keys must be created locally and protected by the OS. Confirmed identity fingerprints are pinned, no public or OS certificate store is consulted, and changed identities require re-pairing. User-visible codes must authenticate the actual handshake or full identity, never a few unauthenticated display fields.

The current crypto API requires the peer certificate plus an independently supplied full 64-hex SHA-256 fingerprint. Both TLS roles require the exact leaf and delegate certificate validity/signature checks to rustls WebPKI with only that pinned certificate as trust root. TLS 1.2, early data, session resumption and QUIC migration are disabled. Human pairing and durable peer trust are not wired yet. Loopback tests are not proof of LAN enforcement.

Local identity persistence uses a versioned, bounded 4 KiB certificate/key record. The transport layer validates lengths, version and key/certificate correspondence. Platform providers create without replacement and never convert denial or corruption into a missing identity. Creation reads back and compares the full fingerprint before returning a usable identity. macOS stores the record in a fixed current-user file-Keychain item. Windows encrypts with current-user DPAPI before any disk write, syncs its temporary file and publishes by an exclusive hard link. Rust plaintext buffers zeroize on drop. Security.framework's immutable returned allocation is OS-owned and cannot be claimed scrubbed by Rust. Native creation, separate-process readback and duplicate rejection passed on both machines. Native failure paths, denied/locked Keychain authorization and packaged-app tests remain required before pairing can enable input.

The Windows adapter reads physical-interface flags and actual routes from IP Helper and Wi-Fi attachment metadata from Native Wi-Fi. A socket-options helper restricts ingress with IP_IFLIST and egress with IP_UNICAST_IF. macOS has equivalent physical-interface, route-query and UDP-option diagnostics. Explicit Mac network diagnostics additionally query a named CoreWLAN interface twice and require matching interface name, station state and raw SSID. The access point's BSSID is not part of it, so roaming within one network is not an attachment change. Missing or inconsistent values remain unknown, without a permission request or scan. Ordinary enumeration skips this query. Attachment bytes are opaque policy state and redacted from Debug output.

Each platform exposes a bounded nonblocking single-datagram receiver for an already bound and interface-pinned socket. It validates native ancillary lengths, source address, destination address and arrival index, rejecting incomplete or conflicting metadata. The receiver owns its configured socket, so closing another socket and reusing its handle cannot redirect a receive call. This low-level receiver does not bind, select a peer or connect Quinn. The guarded endpoint composes it with native setup and exact packet policy.

The optional asynchronous receiver consumes the same configured socket into Tokio and retains its native receive configuration. It does not duplicate a handle or create a socket/runtime itself. Readiness is re-registered after `WouldBlock`, while malformed metadata and other native failures are returned to the owner. This remains the native I/O component beneath the guarded Quinn adapter. Tokio was already present in the resolved graph and is now a direct dependency of both native crates.

Native watcher APIs exist independently of the CLI. Windows registers IP Helper interface/address/route notifications and selected Wi-Fi attachment notifications. macOS checks Dynamic Store dispatch registration and retains callback state across queued work and teardown. Both use the core's cloneable, permanent revocation signal and revoke it before teardown. Native watcher ownership remains on the session owner thread. The guarded endpoint registers before authorizing a fresh snapshot, rejects revocation and wakes an idle endpoint on later changes. These APIs do not create sockets, authorize a peer or enable sharing. Native repeated lifecycle checks passed on both machines. Actual network-change delivery remains a separate validation gate.

## Guarded QUIC ownership

An explicit library call accepts a stable adapter identifier, interface index and exact local/peer IPv4 socket addresses. Ports must be nonzero. Native setup registers the watcher, authorizes a fresh physical attachment and kernel route, binds and pins one owned socket, then repeats the observations. It never accepts a caller-forged network lock or falls back after failure. The public wrapper retains the thread-affine watcher and hides Quinn's rebinding and alternate-configuration APIs. CLI startup never constructs it.

The socket admits one datagram at a time after destination, arrival index and exact peer IP/port checks. At most 32 unwanted packets are consumed per poll before yielding. Native receive failures revoke rather than spin. Sends use the pinned native socket with no source ancillary message that could override macOS interface selection. Segmentation is disabled and ECN is omitted in this initial adapter. That omission is covered by encrypted transport tests, not a latency or congestion-performance claim.

The core signal uses the pinned futures-util AtomicWaker. Only Quinn's endpoint receive driver registers as its observer. Write pollers have independent native readiness futures and only inspect the latch. Revocation wakes that driver, whose terminal I/O error drops Quinn's connection event channels and wakes pending accepts, handshakes, streams and writers. Hard send or writable errors first revoke, then stop sending with `WouldBlock`/`Pending`. Returning those errors directly would abandon Quinn connection cleanup when another connection handle is retained. Only the receive driver emits the terminal error. Unexpected `ConnectionReset` is converted to a terminal error because Quinn otherwise ignores it. Windows disables native UDP ICMP reset reports during socket configuration, preventing unauthenticated ICMP errors from revoking the session. Incoming handshakes recheck revocation after synchronous registration, closing any connection registered after endpoint-driver cleanup. Local failure does not wait for remote close traffic or reset the latch. In-flight kernel work cannot be undone by the post-I/O latch check.

This completes a library composition, not native physical-network validation or the input coordinator. The Mac currently lacks usable attachment metadata, human peer confirmation is still external, and actual network-change notifications need controlled physical tests.

## Display configurations

MonHop keeps a connection to the active computer rather than to a layout. The supervisor (`lifecycle::keep_connected`, a pass every 250 ms plus one the moment the user chooses a computer or ends arranging, through `AppController::nudge`) runs a sharing session while a saved record fits both computers' displays exactly and a setup link the rest of the time, so the pair is never left with neither. The immediate pass is what changes: the connection itself follows within a tick, because the worker for the previous computer or for arranging has to stop before the port is free. A display change is an expected transition, not a failure, wherever it lands. A dial that succeeds and then finds the displays no longer fit records why with `sharing::note_layout_misfit`; a running session the displays outgrew is classified by `sharing::displays_changed_end` and recorded with `sharing::note_displays_changed`, which covers `LocalDisplaysChanged`, the other computer closing with `PeerDisplaysChanged`, and any end after which this computer's displays can be read and no longer match the record the session ran with. A display list that cannot be read while it settles is neither a change nor a failure: the supervisor and the dial re-read it every 250 ms for up to 5 s without a backoff or a banner (`sharing::still_unsettled`). All the display changes end the worker cleanly, keep no failure reason, and leave the reason that opens the link on the next pass, so the pair never waits out a reconnect interval for a record that cannot fit again. Only a worker that ends with a real error — injection refused, a permission gone, a queue overflowed, a health check missed — costs the ten-second backoff, which `sharing::SharingController::within_failure_backoff` holds over the supervisor until it passes or the user chooses again. A peer presenting a certificate other than the paired one (`SetupFailure::PeerIdentityChanged`) stops the worker with a message to pair again and waits a minute before any retry, and identical failed attempts are logged once and then once a minute with a count. The same holds when the two computers take different steps at once: a session dial or a link run that meets the other purpose on the shared port ends at once with `PurposeMismatch` on both sides, because the handshake weighs purpose before control, so a link meeting a session says so on both computers, and the transport does not retry a disagreement. Each computer then moves to the step the other is already in and they meet on the link. Two sessions whose saved records carry different control permissions are the one remaining disagreement; that is `ChangedSinceInspection`, answered on the link rather than by dialing again.

Nothing is promoted without the link. A computer whose displays no longer fit the active record opens the link, and only the decider picks the record there; promoting a memory from one computer's displays alone could leave the two holding different records that each fit their own displays, trading the link for sessions forever. Every file this app keeps for sharing carries a format version, and a file from an older build loads as empty (`sharing_preferences::load_versioned`): the user arranges again, while pairing is untouched.

The lower DeviceId decides what runs next (`sharing_preferences::local_decides`), identically on both computers, so one display change can never leave the two holding different records. When the active record stops fitting while the link is up, the decider waits until both computers' displays have held still for a second (`sharing::displays_settled`), then sends the active record if it fits, else the arrangement remembered for exactly these displays (`ArrangementLibrary::automatic_fit`), else one rebuilt with `sharing_preferences::adapt_to_inspection` from the memory made with exactly the monitors connected now, so a display that only moved keeps every crossing made for it, and from the running record when there is no such memory (links, positions and hidden ids naming vanished displays dropped; a display that appeared joins its own computer's block). Every proposal carries the record's control permissions. It sends that record over the link with `SharingController::propose_layout`, which is the Apply the window performs without the window's revision to check, so both computers stage and commit the same bytes, remember them, and close the link for the session. The other computer adapts nothing of its own: it raises the `peerDeciding` banner and waits for the layout to arrive. A banner appears only where the user has something to do or something was lost. The decider raises `updating` while its proposal is out and `waiting` when nothing fits or adapts. Only a refusal proving nothing fits (the other computer finds the record invalid) raises `waiting` at once; a proposal cancelled, busy, voided by a display change or unsaved is made again a second later, and the third such refusal for the same displays raises `waiting` (`sharing::note_passing_refusal`). At the commit (`sharing::resolve_notice_on_commit`) every banner comes down, with one exception: the decider's `updating` becomes `continued` when the record it sent had to leave something out — a crossing dropped, a position dropped, or a display left unused, which `sharing_preferences::adapt_to_inspection` reports as `left_out` against the record it rebuilt from and which travels with the send. A record remembered for exactly these displays loses nothing and says nothing, a display that only moved keeps every crossing and says nothing, and the computer that merely accepted the other's choice never reports the loss, because one computer reports it and it is the one that chose. A banner is raised once per set of displays, brings the window forward only for `waiting`, never blocks any control, and is cleared by a dismissal, an Apply, or a commit. What stops the supervisor proposing the same displays twice is the proposal it recorded when it sent one, not the banner: a proposal is recorded and its banner raised under the one lock that sends it, and both the record and the link go together, so a proposal lost with its connection is made again on the next one while a banner alone never stands in for an answer. Fit stays exact geometry on both sides; a changed display never runs on stale geometry.

Arranging is told, never inferred. The link carries an `Arranging` frame (one byte, 0 or 1) sent on every connection and on every change, and each computer keeps what the other last said (`LinkEvent::PeerArranging`), forgetting it when the link ends. While either computer's user is arranging, the supervisor neither proposes a layout nor yields the link to a session, so an automatic proposal can never eject someone mid-arrangement. This is why both computers must run the same build: the frame is part of protocol version 9, and a build disagreement already fails the handshake with a message that says so. A build disagreement the handshake itself can name — a peer announcing a different platform or a different feature set — is symmetric like a purpose or control one, so `session_handshake::negotiate_inner` lets the peer read this computer's three frames before closing; both then reach `PeerHelloMismatch`, which becomes `SetupFailure::VersionMismatch` ("install the same build on both computers") and stops the dial instead of one side seeing a broken stream and dialing on. A protocol version skew is caught one layer down: the version sits in the frame header, `monhop-protocol` refuses to decode a frame carrying another one, and `session_wire` names that as `UnsupportedVersion`, which the handshake reports as the same build mismatch. It reaches that verdict through the same read-then-validate result, so it is acknowledged the same way rather than closing at once, and neither side is left a reset stream to keep dialing on.

Every layout applied on both computers that left nothing out is also remembered on each of them, in the arrangement library beside the setup file, as an automatic entry for the exact displays both computers showed (`arrangement_library::remember_automatically`: one entry per pair of display sets, the newest replacing the older, the oldest automatic entry evicted at the 32 cap, named entries never touched). Only automatic entries are ever chosen without the user; named entries exist only where they were saved and stay manual. The library is addressed by the paired computer's identity instead of by a live connection (`views_for`, `remove_for`); the file is this computer's own, so the half of each record naming this computer is informational and nothing has to be resolved before listing. Every paired computer's layout history therefore lists and forgets while it is disconnected, and an entry offers a layout to load only when a live link to that same computer reports the displays it was made with (`fits`). Each computer card also carries the connected computer's live displays beside its saved ones (`SavedSetupView.live`), so a card shows what is there now rather than what was there at the last Apply.

The two Home switches edit the active record's control map (`control`, keyed by both computers' full fingerprints, at least one true; `sharing_preferences::wire_control` maps it to the wire permissions the same way on both computers). `SharingController::set_control` refuses turning off the last direction and records the change as pending; the supervisor ends the session deliberately (`end_session_for_control`, no failure line and no backoff), opens the link and proposes the record with the change applied, both computers commit, and the next pass starts a session with the new permissions. While the change travels the view reports it as syncing with the proposed values, so a switch never snaps back; a simultaneous change from the other computer that wins the link's tie-break supersedes it (`reconcile_pending_control`).

A display is the same display by its monitor's EDID identity (vendor, product, serial; `DisplaySnapshot::monitor`, carried on the wire), not by its OS id. On Apple silicon the Core Graphics display id is a per-connection number that changes whenever a monitor is reconnected, and Windows can renumber `\\.\DISPLAYn` after a topology change, so a layout keyed by id would never fit again after a replug. `sharing_preferences::pair_displays` pairs remembered displays with live ones by identity where both report one for exactly one display (two identical monitors without serials fall back to ids), and by id where either lacks it; two displays with different identities never pair, even on a reused id. A fit (`remap_to_inspection`, `remap_to_local_displays`) then rewrites the record's display ids to the live ones before it is promoted, offered as a named arrangement, or adapted, and the promoted record is remembered again so the memory carries the current ids. Records saved before identities were recorded keep matching by id.

## Updates

The desktop `updates` module is the only code that reaches beyond the local network. It asks the pinned endpoint in `tauri.conf.json`, this repository's latest GitHub release, for `latest.json` through `tauri-plugin-updater` (20 s timeout, no other endpoint; a debug build may point at a loopback host through the build-time `MONHOP_UPDATE_ENDPOINT`), only when the `updates.json` preference keeps automatic updates on and a computer is paired (30 s after launch, then every 6 h) or when the user presses Check now. A found build is downloaded into memory, where the plugin verifies its minisign signature against the public key compiled into the app before the bytes are ever kept; an unsigned or foreign build is discarded with a plain message. The verified bytes are installed on the way out or when the user presses Restart to update, which is refused while a sharing session is active. On the way out the controller drains first (`AppController::drain_for_exit`, bounded to 5 s) and the install is bounded to 5 s and never on the network; a tray Quit raises `RunEvent::ExitRequested`, while Cmd+Q, an AppleScript quit and logout on macOS reach only `RunEvent::Exit`, so both events drain and install, and the second call is a no-op. On Windows the plugin starts the installer and exits the process itself, so the controller is drained first through the plugin's `on_before_exit` hook. Plugin errors never reach the window or the log as text, because they can carry addresses; `describe` maps them to four sentences. The `--check-ui` smoke run never schedules or performs a check. The About card's three links are a fixed Rust allowlist (`links.rs`); the window names a target, never a URL.

## Releases

The version lives once, in `[workspace.package]` of the root `Cargo.toml`; every crate inherits it and `tauri.conf.json` carries no copy, so the bundle names, the About card and the updater's comparison all read the same number. `CHANGELOG.md` keeps an Unreleased section that is curated as work lands. `scripts/release.py` cuts a release from a clean, synced `main`: it bumps the workspace version and the intra-workspace pins, refreshes `Cargo.lock` and the dependency reports, moves the Unreleased section under the new version, commits `Release vX.Y.Z` and tags it. Pushing the tag runs `.github/workflows/release.yml`: the `ci` workflow's gates, then the `build` workflow's matrix (Apple silicon, Intel, Windows NSIS) uploading installers, signed updater bundles and `latest.json` into a draft release on this repository, then a publish job that refuses to undraft until the tag matches the workspace version and `latest.json` carries all three platforms. The updater only ever reads the latest published release, so a partial build is never visible to installed apps. The same `build` workflow runs on demand without a tag and leaves the images as workflow artifacts. `docs/RELEASING.md` is the runbook.

## Start at login

The desktop `autostart` module keeps one preference, `autostart.json` (`enabled`, default on), and registers MonHop with the operating system only from two explicit user actions: applying a layout on both computers (the onboarding switch, on by default) and flipping the switch in Settings. Starting the app never reads, writes or repairs the registration, and forgetting the last paired computer removes it, so a registration exists only while the switch is on and a computer is paired. On macOS the registration is `SMAppService` for the launch agent bundled at `Contents/Library/LaunchAgents/com.manuelgozzi.monhop.login.plist`, which starts the app's own executable with `--login`; on Windows it is the `MonHop` value under the user's `Run` key with the same argument, and the `StartupApproved` entry tells the Settings card when the user turned it off in Windows Settings. A login launch creates the main window hidden and shows only the tray; the supervisor then reconnects to the active computer as after any launch. No shell command is involved on either platform.

## Screen dimming

MonHop owns screen dimming: the desktop `dimming` module keeps the preference (shortcut on or off, darkness 10 to 99 percent in whole percents), the Home card controls it, and `dimming/macos.rs` and `dimming/windows.rs` draw one black click-through, capture-excluded, topmost window per display and register the system-wide chord (Ctrl+Alt+0 on Windows, Control+Option+0 on macOS, the same physical keys). The chord acts on the computer that receives the keystrokes, so a press forwarded to the other computer dims the screens the user is looking at. MonHop never treats its overlays as displays or routable targets, and never changes monitor resolution, power state or gamma. When another application already holds the chord, registration fails and the Home card says MonHop is waiting; the thread that owns the chord then asks for it again on a backoff (5 s, doubling to 60 s), takes it the moment it comes free, and stops as soon as the shortcut is switched off or the app is on its way out.
The `--check-ui` smoke run loads the dimming preference without registering the chord.

## Timer resolution on Windows

Captured input wakes the source loop the moment the hook thread queues it (the capture queue runs a registered waker after every publish), and the loops otherwise tick every millisecond for housekeeping. Windows schedules timers at 15.6 ms unless the process asks for less, which turned captured motion into 64 Hz bursts that the other computer injected one position at a time. The desktop raises the process timer period to 1 ms (`timer_resolution.rs`) for its whole life and restores the default on a clean exit; macOS timers need nothing.

## Setup shell boundary

The Tauri shell bundles static local HTML/CSS/JavaScript. The main window is transparent over native vibrancy (an always-active NSVisualEffectView HUD material on macOS, Acrylic on Windows) and every CSS surface is a translucent layer; the macOS private-API feature is enabled only so the webview background can be transparent. The header's theme toggle cycles system, light and dark: the choice is saved in `appearance.json`, the CSS pins it through `html[data-theme]`, and Rust applies it to the native window theme so the vibrancy material follows. Its only native commands are an explicit diagnostic snapshot, standard macOS permission prompts and two fixed privacy-settings links. Startup does not invoke them. No input or transport action is reachable from the UI. The permission guide uses local CSS animation with pause and reduced-motion support.

The main window permits only its exact platform-local origin and entrypoint, denies new windows/downloads and has an exact three-command capability. A pinned runtime patch denies URLs that fail parsing before the application callback. A pinned Tao patch removes initial Windows raw-input registration; the app additionally filters all device events. Windows initializes COM before supplying a custom WebView2 environment with automatic crash upload disabled. These controls need native enforcement and engine-network testing, not just source/unit checks.
